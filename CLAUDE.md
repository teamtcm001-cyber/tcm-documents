# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

TCM Document Agent — a construction-document management app for a Thai engineering company (TCM). Team members upload/version project documents (EIA, drawings, contracts, MOM, BOQ, etc.), and search them via a bilingual (Thai/English) AI-assisted chat. React + Vite frontend, Supabase (Postgres + Auth + Storage) backend, deployed on Vercel with serverless functions (AI chat via the Anthropic API, Google Drive storage).

Note: the AI MOM Writer (voice/transcript to Minutes of Meeting) and its local-Whisper transcription were removed from the app; see "Removed: MOM Writer" below.

## Commands

```bash
npm install         # install deps
npm run dev          # start Vite dev server on http://localhost:5173
npm run build        # production build -> dist/
npm run preview      # preview the production build locally
npm run deploy       # vercel deploy --prod
```

There is no test suite or linter configured in this repo — don't invent `npm test`/`npm run lint` commands.

Environment variables (see `.env.example`) go in `.env.local` for local dev:
- `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — required for the app to function at all (auth/db/storage).
- `ANTHROPIC_API_KEY` — set only in Vercel (server-side, used by `api/chat.js`). When absent, the serverless function and client both fall back to non-AI behavior (see "AI features degrade gracefully" below).

## Architecture

### Two independent apps in one repo
- **`src/` (the real app)** — React 18 + Vite SPA, entry `src/main.jsx` → `src/App.jsx`. This is what `npm run dev`/`npm run build` operate on and what's deployed.
- **`qto/` + `TCM_QTO_Agent.html`** — a separate, self-contained "QTO Agent" (quantity take-off) tool: plain JS modules loaded directly by a standalone HTML file, no build step, no Supabase. The user pastes their own Anthropic API key into the page (stored in `localStorage`) and it calls the Anthropic API directly from the browser. Unrelated to the Vite app's routing/build.
- **`TCM Document Agent.html`** is a legacy pre-Vite prototype (references `src/data.js`, `src/icons.jsx`, etc. that no longer exist under `src/`). It is not part of the current build — don't treat missing files it references as a bug.

### Data model (Supabase Postgres, see `SQL_SCHEMA.sql` / `MIGRATION_CONTENT_SEARCH.sql`)
- `projects` — one row per construction project (`code` is the human-facing short id, e.g. `MRT-PP`). Still has legacy columns `mom_topics`, `mom_logo`, `mom_font` (per-project MOM template config) that nothing in the app reads or writes any more; they are intentionally left in the DB (see "Removed: MOM Writer").
- `files` — a document row per uploaded version. Versioning is by `(project_id, type, base_name)`: each upload marks prior rows with the same base_name as `is_latest = false` (done client-side in `uploadFile`, see `src/api/supabase.js`). `content_text` holds extracted plain text used for search (nullable — code must tolerate the column not existing yet, see the retry-without-content_text logic in `uploadFile`).
- `activity` — timeline/audit log per project.
- `projects.has_installments` (optional until `scripts/project-billing-flag.sql` is run) — see "Per-project switch โครงการนี้ไม่มีงวดเบิก" below.
- `profiles` — one row per person allowed in (`role` admin|exec|user, `active`, `must_change_password`); `project_members` — per-project access (`manager`/`editor`/`viewer`, one row per project+user). Both come from `scripts/auth-01-foundation.sql`; the `manager` role and the member RPCs come from `scripts/auth-04-project-managers.sql`.
- Storage bucket `documents`: object keys are sanitized ASCII-only (`sanitizeStorageKey` in `src/api/supabase.js`) because Supabase Storage rejects non-ASCII (e.g. Thai) keys — the real filename is preserved separately in the `name` column for display/download.

### Per-project switch "โครงการนี้ไม่มีงวดเบิก" (`projects.has_installments`)
Some projects have no billing installments at all (e.g. a Hybrid project with no Pre-con งวดเบิก). `projects.has_installments boolean not null default true` comes from `scripts/project-billing-flag.sql`; `project_tracking_overview` exposes `has_installments` and returns NULL / 0 for every installment-derived column when it is false (the installment rows stay stored, just hidden).
- **Tolerance**: until that script has been run the column is ABSENT from every row. `hasInstallments(row)` in `src/utils/tracking.js` treats absent / null / anything but the boolean `false` as "has installments" (today's behaviour). Writing the flag when the column is missing (`isBillingFlagColumnMissing`: 42703 / PGRST204, or no code + "could not find / does not exist", and ONLY when message / details / hint actually name `has_installments` - an unrelated or empty-message 42703 / PGRST204 is never taken for it) throws `BILLING_FLAG_MISSING_MESSAGE` ("… ต้องให้ผู้ดูแลระบบรันสคริปต์ project-billing-flag.sql ก่อน …"); nothing is half-saved.
- **Who may change it (user decision)**: ONLY an admin or the manager (Project Co) of THAT project (`canManageProject(projectId)`); editors, viewers and execs see the state read-only. The database enforces it: a trigger of `project-billing-flag.sql` raises SQLSTATE 42501, message `BILLING_FLAG_FORBIDDEN` (Thai detail) when anyone else CHANGES the value (sending the current value is not a change). `writeError` keeps the database error as `cause`; `isBillingFlagForbidden` recognises it and the write throws `BILLING_FLAG_FORBIDDEN_MESSAGE` "เฉพาะแอดมินหรือผู้ดูแลโครงการเท่านั้นที่เปิด/ปิดได้" (AppError code `forbidden`, also shown as a toast because the switch disappears) after the usual `'denied'` access re-read (so a manager demoted meanwhile loses the switch). The project-creation checkbox is admin-only like project creation itself.
- **Write**: only through `updateProjectTracking(projectId, { has_installments: boolean })` -> `writeBillingFlag` (boolean only, must be sent ON ITS OWN - combined with other fields it is refused). The UPDATE is conditional (`.neq('has_installments', value)`): a stale page or double submit that sends the value already stored changes nothing and writes NO activity line; 0 rows is told apart from an RLS refusal by re-reading the row (`_unchanged: true` when it already had that value, otherwise "no access" + `'denied'`). A real change writes one activity line "แก้ไขข้อมูลเบิกงวดงาน: ตั้งค่าเป็นโครงการที่ไม่มี/มีงวดเบิก" (the DB trigger writes the admin-only audit row). `NewProjectModal` offers the same checkbox (default OFF = has installments); `createProject` sends `has_installments: false` only when ticked and, if the column is missing, creates the project without it and returns `_billingFlagNotSaved` (toast tells the admin to run the script).
- **Tracking detail** (`TrackingInstallments.jsx`, `NoBillingSwitch`): checkbox "โครงการนี้ไม่มีงวดเบิก" rendered only when `TrackingDetail` passes `onSetHasInstallments` (= `canManageProject`). It sits at ONE position right under the panel header in both states, so toggling never re-mounts it; while saving it is `aria-disabled` + a ref lock (never `disabled`, which would drop keyboard focus) and focus is put back on it after every save / cancel / Escape. Turning it ON while NON-CANCELLED installments exist (same count as the header "เบิกแล้ว x/N") asks first (ConfirmDialog "งวดที่มีอยู่ N งวดจะถูกซ่อนและไม่นำมาคิดสถานะ — ข้อมูลยังเก็บไว้ เปิดกลับได้"); only cancelled ones = no confirm; turning it OFF needs no confirm and the stored installments reappear. When ON the panel shows a muted note "โครงการนี้ไม่มีงวดเบิก" (people who can edit also see "งวดที่บันทึกไว้ N งวดถูกซ่อนไว้", N = non-cancelled) instead of the list, the add form and the checklists / templates; editors / viewers / execs see it read-only. After a successful write `setBilling` re-reads the overview row; if that re-read fails (or the view lacks the column) the row on screen still gets the SAVED value, with only the success toast. A failed write shows its message in the dialog (or inline under the switch).
- **Health / overview**: `computeHealth` fires NO installment rule for such a project (overdue, ready-to-bill aging, due soon with missing documents - even if stale numbers or a `readyToBillDays` come along) and returns `noInstallments: true`; the % complete / time-elapsed / stale rules still apply. `nextInstallmentLine` returns `{ text: 'ไม่มีงวดเบิก', tone: 'mute', noInstallments: true }` (never "ยังไม่มีงวดงาน"); the overview card shows a neutral badge "ไม่มีงวดเบิก" instead of next installment / documents / counts, and the banner's overdue total skips it. The "ดูเกณฑ์" popover says so. The Dashboard cards show no installment info, so nothing changes there.
- **AI chat**: `buildProjectBrief` sets `noInstallments: true` (and an empty installment list, `trackingAvailable` NOT false even if an installment read failed) for such a project; `buildGrounding` never reads its installments. The documents scan (`docsScan`) counts them as `projectsNoBilling`, apart from `projectsWithoutInstallments` ("ไม่มีข้อมูลงวด" / ตรวจไม่ได้) and `projectsUnreadable`; `selectBriefRows` ignores their stale numbers. Server (`api/chat.js`): `sanitizeBrief` keeps `noInstallments` only for the boolean `true` and then drops any installments sent along; `renderBrief` writes "งวดงาน: โครงการนี้ไม่มีงวดเบิก (ตั้งค่าไว้)" (`trackingAvailable:false` still wins); DOCS_SCAN renders "- N โครงการไม่มีงวดเบิก (ตั้งค่าไว้) …" on its own line (`projectsNoBilling` is a clamped number like the others); rule 10 and the DOCS_SCAN rule tell the model never to call them "ไม่มีข้อมูลงวด" / "ตรวจไม่ได้" / missing documents. The local (no AI) answer prints "• งวดงาน: โครงการนี้ไม่มีงวดเบิก (ตั้งค่าไว้)" for a status question and, for a documents question, a line "N โครงการไม่มีงวดเบิก (ตั้งค่าไว้)" after the answer itself.
- Tests (synthetic data, git-ignored local harness, not part of the repo): `.tests-local/unit/billing-flag.test.mjs`, `.tests-local/ui/billing-ui.mjs` (Playwright on the in-memory fake, with and without the column, trigger emulated) and `.tests-local/ui/qa/billing-pg-journey.mjs` (real PostgreSQL 17 + the real scripts and SPA; `STRICT=1 bash .tests-local/ui/qa/run.sh`); `bash .tests-local/runall.sh` rebuilds the SPA for the fake and runs every preserved suite. Not verified against the live DB / Supabase's PostgREST.
- 390 px: the tracking detail grid uses `minmax(0, 1fr)` + `min-width: 0` on its items, so the progress panel / installment cards wrap and only the history table and the status stepper scroll inside their own `overflow-x: auto` containers.

### `src/api/supabase.js` is the single data-access layer
All DB/storage/auth calls go through this file (no other module talks to Supabase directly). Components import named functions from it (`fetchProjects`, `uploadFile`, `fetchActivity`, `getFilePublicUrl`, etc.) rather than using the `supabase` client directly.

### Authentication and access (real per-person login)
- Email + password login (`supabase.auth.signInWithPassword`); there is no self sign-up and no email recovery — an admin creates accounts and resets passwords through `POST /api/admin-users` (service-role key, server only). The temporary password is returned once and must never be stored or logged. The old shared-account auto-login, `NameGate`, `logVisit` and `localIdentity` were removed.
- `src/auth/AuthContext.jsx` owns the gate (loading → login → forced "ตั้งรหัสผ่านใหม่" when `profiles.must_change_password` → app, plus a blocking "account disabled" screen) and exposes `useAuth()`: `profile`, `role` (`admin | exec | user`), `memberships` (`project_members` of the signed-in user, fetched once), `canEditProject(id)`, `canManageProject(id)`, `canUploadAny`. UI gating mirrors RLS (admin edits all, exec is read-only everywhere, user edits only projects where `project_members.role` is `editor` or `manager`; only an admin or the `manager` of THAT project manages its people via `canManageProject`) — RLS (`scripts/auth-01-foundation.sql`, `auth-02-enforce-rls.sql`) is the real enforcement.
- **Per-project roles** (`project_members.role`, labels in `src/utils/roles.js`): `manager` "ผู้ดูแลโครงการ", `editor` "แก้ไขได้", `viewer` "ดูอย่างเดียว". A manager edits like an editor (all `canEditProject` gates: tracking, upload list, drawer actions, status, re-index) AND adds / removes / re-roles the people of their own projects without being a global Admin, AND (with admins, unlike editors) toggles the project's "โครงการนี้ไม่มีงวดเบิก" switch. Project create/delete and the "ผู้ใช้และสิทธิ์" console stay Admin-only. Rules decided with the user: (1) only EXISTING, active `user`-role accounts can be added (account creation stays Admin-only; admin/exec/inactive accounts are never addable); (2) a manager can appoint other managers in their own project but cannot change or remove their own row (the UI shows "คุณ" with no controls; the RPCs refuse with `SELF_CHANGE_FORBIDDEN`); (3) people are found by typing the FULL e-mail — the organisation's users are never browsable, and an e-mail is shown only for existing members of the project or after an exact match.
- **Member panel**: `ProjectDrawer` shows a tab "สมาชิกโครงการ" (`src/components/ProjectMembersPanel.jsx`) only when `canManageProject(project.id)` (admins see it on every project); documents tab is unchanged for everyone else. List sorted manager → editor → viewer with an inactive-account marker; role `<select>` + remove (ConfirmDialog) per row; appointing a manager needs a ConfirmDialog, and so does demoting someone who currently is a manager (other role changes are one click); only the latest list load may set state (sequence guard), and the add form's "found" card follows the list so it never shows a stale role; one global write lock (ref) so double clicks send one request; `refreshAccess()` is not called after a successful write (the server refuses changes to one's own row and a successful write proves our rights were valid); if another manager/admin changes this person's rights meanwhile, the next write answers FORBIDDEN and the `'denied'` path re-reads memberships. If the signed-in manager's own role was changed meanwhile, the server answers FORBIDDEN, the data layer reports `'denied'`, `AuthContext` re-reads memberships and `App` drops the open drawer (existing `accessVersion` behaviour).
- **Member RPCs** (all through `src/api/supabase.js`; named args exactly as declared; errors arrive as PostgREST errors with `code` = SQLSTATE and `message` starting with a keyword): `list_project_members(p_project)` → `{user_id,email,full_name,role,active}`; `find_user_for_project(p_project,p_email)` → 0 or 1 row `{user_id,email,full_name,member_role}` (0 rows = not found OR not addable, shown as ONE generic Thai message, never distinguished); `set_project_member(p_project,p_user,p_role)` and `remove_project_member(p_project,p_user)` → void. Data-layer helpers: `listProjectMembers`, `findUserForProject` (trims/lower-cases, rejects empty / >254 chars / no `@` client-side), `setProjectMember`, `removeProjectMember`. Error mapping (`memberRpcError`): 42501/`FORBIDDEN` → `forbidden` (+ `'denied'` event), 42501/`SELF_CHANGE_FORBIDDEN` → `self_change` ("ไม่สามารถแก้ไขหรือลบสิทธิ์ของตัวเองได้", no re-read), P0002/`TARGET_NOT_ELIGIBLE` → `target_not_eligible`, P0002/`PROJECT_NOT_FOUND`, 22023 → `bad_request`, PGRST301/401 → `unauthorized` (+ `'expired'` event), PGRST202/404 → `not_available` (migration not applied), 503/PGRST002 → `auth_unavailable`, network → `network`; 23503 (account deleted between lookup and write) → `target_not_eligible`.
- The Admin console's per-project matrix (`setMembership`, table write) offers all of ผู้ดูแลโครงการ / แก้ไขได้ / ดูอย่างเดียว / ไม่มีสิทธิ์; its summary counts the managers too. If the DB still has the old CHECK (auth-04 not applied) the write fails with 23514 / `project_members_role_chk`; `setMembership` turns that into a Thai `not_available` AppError ("ยังบันทึกบทบาทผู้ดูแลโครงการไม่ได้ — ต้องให้ผู้ดูแลระบบรันสคริปต์ auth-04 บนฐานข้อมูลก่อน") instead of raw database text.
- **Bulk onboarding from Excel** (admin only; button "นำเข้าจากไฟล์ Excel" in the console, `src/components/AdminImport.jsx`): the admin picks a `.xlsx` (sheets 'Project List' = [ชื่อโครงการ, Project Co.1, Project Co.2], 'Name List' = [NO., Name-Sername, Email, ID, note]); the file is read IN THE BROWSER (`xlsx`, lazily imported), a PREVIEW PLAN is shown and nothing is written until "ยืนยันนำเข้า". Pure logic with no Supabase import (unit-testable in node): `src/utils/importPlan.js` (read + parse, project auto-match, person match, `buildPlan`, `planSignature`) and `src/utils/importRun.js` (sequential executor with injected deps). Rules decided with the user:
  - **Reading / limits**: sheets found by exact name first ('Project List' / 'Name List'), then loosely, then by content; hidden / veryHidden sheets are ignored; the chosen sheet names are shown in the preview header. `XLSX.read` uses `sheetRows` and the DECLARED range (`!fullref`/`!ref`) is checked BEFORE anything is materialised: more than 3000 rows or 50 columns (e.g. a stray cell at XFD1048576) = a Thai "ใหญ่เกินไป" error; more than 1000 people or projects = refused. Header columns by name (with a header row the ID column must be named ID, otherwise everybody gets a random password + a warning; column D is only a fallback when there is NO header row at all); blank rows / stray header rows ignored. A Co cell with several coordinators (`, / ; & และ` or new lines) is split before matching and stored joined by ", ". Names / e-mails starting with `= + - @` are rejected; an e-mail is only trimmed + zero-width-stripped + lower-cased (whitespace INSIDE an address = row skipped, never merged) and validated like the server's `vEmail` (ASCII).
  - **People**: e-mail already in the system -> left completely alone (a sheet "Admin" on a plain-user account only WARNS); otherwise created through `adminCreateUser`. Role `admin` ONLY when a whole note cell is `Admin` / `แอดมิน` / `ผู้ดูแลระบบ` (optionally + a number, e.g. "Admin 2"; never "Office Admin", "not admin", "Administration"); a duplicate-email row never escalates the earlier row. The confirm dialog lists every person who will become a GLOBAL ADMIN and, when such an admin gets the employee-ID password, requires a checkbox acknowledgement (anyone knowing e-mail + ID could take the account over before the owner logs in). Option "ใช้รหัสสุ่มสำหรับแอดมิน (แนะนำ)" (default OFF - the user asked for ID passwords) sends a random password for role admin only.
  - **Passwords**: option ON (default) sends the ID column as `initialPassword` (the person is still forced to change it at first login; no temporary password comes back). The ID is used only if its cell is TEXT, or an integer cell of at most 12 digits shown as digits (warning: leading zeros may be lost); dates, floats, scientific formats (`1.2E+10`), formulas and booleans are unusable -> flagged, random password. A person without a usable ID, or the option OFF, gets a server random password shown ONCE in the result with copy buttons (the result dialog cannot be dismissed by Escape / X / backdrop while such passwords are displayed). IDs shorter than 6 characters are flagged; Supabase's "Minimum password length" may reject short IDs - the run reports `weak_password` per person with a hint.
  - **Projects**: a sheet project is pre-selected ONLY when its normalised name (case / spacing / punctuation-insensitive, Thai-safe) is IDENTICAL to a system project name (or code) and unique; a system project is pre-selected for at most one row. Near names are shown as a one-click suggestion ("ใช้ <project> ?") per row and are NOT applied until pressed. A difference in a marker / trailing token (letter suffix A/B, "Phase n" or a number on one side only) is a mismatch and is not even suggested. Two rows on the same system project BLOCK the confirm (error shown outside the collapsed warnings). The confirm dialog states how many projects matched exactly vs were chosen manually. Unconfirmed rows are never written.
  - **Project Co**: `projects.project_co` is set to the sheet names joined by ", " only while empty - the write is conditional (`setProjectCoIfEmpty`: `update ... where id = ? and (project_co is null or project_co = '')`, 0 rows = "filled meanwhile", kept) and touches no other column. Each named Co person who EXACTLY matches (normalised, titles stripped, multi-word) a Name List person becomes `manager` via `setMembership` (none -> add, editor/viewer -> UPGRADE, manager -> keep; global admin/exec and inactive accounts skipped). Single-word names, token-subset and near-identical (>= 12 characters) names are only "candidates" ("ชื่อใกล้เคียง — ตรวจสอบ"), applied only when the admin ticks the per-line checkbox. Unmatched / ambiguous names only warn; Co text `Admin` = text only, no membership.
  - **Idempotent**: a second run plans nothing ("ไม่มีอะไรต้องทำ").
  - **Run rules**: sequential; busy lock; the confirm step re-reads users / projects / memberships and, if the plan changed since the preview, returns to the preview instead of writing; the WHOLE run stops on 401/403/429/503/network and after 3 consecutive upstream-style failures (`upstream_error` / unknown / 5xx - the API maps GoTrue throttling to 502); per-person failures never abort the others (`weak_password` -> hint; `email_exists` = existing, and if that account turns out to be admin / exec / inactive it gets no manager row; `orphan_auth_user` is NEVER adopted in bulk -> "ต้องสร้างทีละคนในหน้าผู้ใช้"); a person whose account failed gets no memberships. Counts always add up (`ok + failed + skipped + notRun = total`); `runImport` never throws and an unexpected error ends the run as `stopped` with a result screen (never stuck on "running").
  - **Employee IDs are secrets**: kept only in memory (non-enumerable `employeeId` on the parsed person, read via `getInitialPassword`), dropped at once for people who already exist and for everybody when the result stage is reached (`parsed` is cleared); never rendered (the preview shows only "รหัสผ่าน: รหัสพนักงาน"), logged, stored or put in results / errors; they appear only in the body of the create request.
  - Data-layer additions in `src/api/supabase.js`: `adminCreateUser({ ..., initialPassword })`, `fetchProjectsForImport()`, `fetchAllMemberships()` (paged), `setProjectCoIfEmpty()`. Performance: projects are indexed once per snapshot (`prepareProjectIndex`), exact names via a map, fuzzy candidates shortlisted by trigram overlap; the Name List is indexed once (`makePersonIndex`, memoised per Co string); the preview pages the lists (200 people / 100 projects at a time) and big selects render their options lazily.
- Calls to our own `/api/*` functions (chat, drive-upload-session, drive-upload-discard, drive-url, admin-users) must go through `authFetch` in `src/api/supabase.js` (adds the Bearer token, refreshes once on 401, reports 401 → "เซสชันหมดอายุ" and 403 `account_disabled` → blocked screen).
- The browser never receives a Google credential. Uploads use a server-created resumable session (`src/utils/googleDrive.js`): `POST /api/drive-upload-session { projectId, name, size, mimeType }` (project edit gate, server-side) returns `{ uploadUrl, driveId, ticket, expiresAt }`; the browser PUTs the bytes straight to `uploadUrl` (no Authorization header, real XHR progress, resumes up to 3 times after a dropped or stalled (no progress for 120 s) connection/5xx/bare 308 via `Content-Range: bytes */<size>`; one fresh session if Google answers 404/410 or a probe returns 308 without a readable `Range` header, never more than one restart per file; a completion probe with an empty body is accepted with the announced `driveId`, and a `size` in the answer must equal `file.size`) and the id Google returns must equal `driveId` (otherwise the upload is an error and nothing is saved). `files.storage_path` = that Drive id. If saving the row is definitely rejected (4xx RLS/check/not-null; never 23505, never a network/5xx/unknown outcome) and a re-select by `storage_path` finds no row, `uploadFile` calls `POST /api/drive-upload-discard { ticket }` to remove the orphan - the server moves it to the Drive trash (recoverable), it does not delete it permanently (409 `in_use` = a row exists, nothing touched); the server re-checks too. Empty files (0 bytes) are refused by `UploadModal` before any upload (the server requires size >= 1), and the dialog cannot be closed while an upload is running.
- Files are only served through short-lived signed URLs: `getSignedFileUrl(fileId)` → `POST /api/drive-url` (takes the `files.id` row id, not the Drive id) → `/api/drive-file?...sig=...`. Previews, downloads and re-index all mint a fresh URL first; a `link_expired` answer is retried once.
- The audit trail (who did what) is written by database triggers and is admin-only; the UI deliberately shows no uploader/updater names for new data (`uploader_name`, `activity.user_name`, tracking `updated_by` stay null/'-').
- Server env vars (never `VITE_`): `SUPABASE_SERVICE_ROLE_KEY`, `DRIVE_URL_SECRET` (>= 32 chars), plus the existing Google ones, and the optional `APP_ORIGINS` (comma-separated browser origins allowed to request upload sessions when the app is served from a host that differs from the request `Host` header, e.g. behind a proxy). See `.env.example`.

### ZIP download of selected documents (`src/utils/zipDownload.js`, `src/components/ZipDownload.jsx`)
Everyone who can view a project can download documents as ONE zip (admin / exec / viewer / editor / manager); RLS decides per file (`/api/drive-url` simply leaves files the person cannot see out of its answer, so they are reported as "ไม่พบไฟล์ หรือไม่มีสิทธิ์" and never fetched).
- **Entry points** (all use `useZipDownload()` from `ZipDownload.jsx`, `zip.begin({ files, projectCode, scope, confirm })`, and render `{zip.dialog}`): project drawer (checkbox per file row, "เลือกทั้งหมด (displayed rows) / ล้างที่เลือก", sticky bar "เลือก N ไฟล์ (ขนาดรวม …)" + "ดาวน์โหลด Zip"; the checkbox selects the DISPLAYED version; "Zip ทั้งโครงการ" = latest versions after a confirm dialog with count + size + the size rules), dashboard card button "Zip ล่าสุด" and the AI chat `download_zip` pill (both = `zip.beginProject(project)`, same confirm), AI chat (the pill zips the latest files of that project; list / summary answers with >= 2 files get checkboxes, all ticked by default, and "ดาวน์โหลดที่เลือกเป็น Zip"). A selection starts at once (no confirm) unless the Blob fallback would be over the cap or the zip is large (> 100 files or > 2 GB): then the dialog shows the rule / an "อาจใช้เวลานาน" warning first. "Zip ทั้งโครงการ" always reads the COMPLETE list through `fetchProjectFilesForZip` (src/api/supabase.js: pages with `.range` until the exact count, no `content_text`; PostgREST answers at most 1000 rows per request) so the confirm shows the true count; the drawer's selection only ever holds the rows on screen (search / type filter / "ล่าสุด" drop ticks that disappear); chat-listed files are zipped only when their id exists in the chat's local index (name / size / project are taken from the local row; the rest are dropped and counted in a toast).
- **Library**: `client-zip` 2.5.1 (MIT, 6.4 kB min / 2.7 kB gzip, STORE only - PDFs/images are already compressed, UTF-8 name flag, Zip64), lazy `import('client-zip')` on the first download only (own chunk, main bundle untouched by the library).
- **Bytes**: only through the existing `GET /api/drive-file` proxy (no bytes ever go through another function; nothing is uploaded to us). Signed links come from the batch form of `POST /api/drive-url` (`getSignedFileUrls`, <= 50 ids per call; the zip code asks for 10 at a time, just in time, and mints again after 3 minutes), each file is read with `Range` requests of 16 MB (`RANGE_CHUNK`) so no request is long or large (a 200 MB PDF = 13 short invocations of `drive-file`; the drive-file function honours a single `bytes=a-b` range and sets Content-Length / Content-Range). Content-Length is trusted only when present AND the body is not Content-Encoded (chunked / gzip answers have no usable length); truncation is caught by the Content-Range check. A chunk that fails (network, stall 60 s, 5xx/429, truncated body) is re-fetched up to 3 times; 403 `link_expired` re-mints the link once. The FIRST chunk of every file is read before the entry is added, so a missing / forbidden / broken file is skipped and listed ("ไม่สามารถรวมไฟล์เหล่านี้ได้") while the others still zip; a failure of a LATER chunk of a file > 16 MB ends the whole run (its bytes are already in the archive) and says which file.
- **Output**: Chrome / Edge (`window.showSaveFilePicker`, opened synchronously in the click that starts the run - browsers require the gesture) stream the zip straight to the chosen file (any size; memory = one chunk); cancel / failure aborts the writable so the partial output is never committed (the browser may leave an EMPTY 0-byte file at the chosen path - the dialog says so). Closing the save dialog is silent. Everything else (Firefox, Safari, mobile) builds a Blob in memory and saves it with `<a download>`; refused above `ZIP_BLOB_CAP_BYTES` = 600 MB on desktop and 150 MB on phones / tablets (`ZIP_BLOB_CAP_MOBILE_BYTES`, by user agent; the message says so; the archive is kept as ~8 MB Blob groups, not duplicated) (estimated from the files' sizes before anything is fetched, enforced again on the real bytes) with a Thai message suggesting fewer files or Chrome / Edge. File sizes in `files.size` are KB (rounded), so totals are estimates.
- **Names**: entries are FLAT, the document's real file name made safe (`safeEntryName`: no `/ \ : * ? " < > |`, control and bidi-override characters, no leading/trailing dots or spaces, Windows reserved names prefixed, <= 180 chars keeping the extension) and unique case-insensitively after NFC normalisation ("name (2).pdf"); <= 200 UTF-8 bytes keeping the extension, zero-width characters removed; the failed-file list shows the sanitised names. Zip name: `<project code>_<Buddhist yyyy-mm-dd>.zip`, or `เอกสารที่เลือก_<date>.zip` when the files come from several projects.
- **Progress dialog** (shared `ui/Dialog`): "กำลังรวมไฟล์ n/N", current file, bytes, ยกเลิก (AbortController; Escape / backdrop / X are disabled while running, same pattern as UploadModal), final counts and the failed list. One run at a time (ref lock + disabled buttons; "ยกเลิก" is armed 0.7 s after the run starts so a double click on the confirm button cannot cancel it). Every await of the run observes the abort signal (picker, dynamic import, createWritable, the signed-link request which also has a 30 s stall timeout, pipeTo), so Cancel ends the dialog at once; if it still has not ended 15 s after Cancel a "ปิดหน้าต่าง" button force-closes (aborts everything, discards the run). The dialog shows "finished" BEFORE the best-effort activity write (8 s timeout). A `beforeunload` guard is active only while a zip is running.
- **Audit**: one `activity` row per project that got files, `action = 'download_zip'`, details "ดาวน์โหลด Zip N ไฟล์" (no names), best effort. `activity_insert` needs `can_edit_project`, so viewers / execs download but are NOT logged (the UI does not even try).
- Tests of this feature live outside the repo (no test suite here): Playwright on an in-memory fake + a real PG17 journey with the repo's RLS scripts. Not verified against real Google Drive / Vercel (large files, `maxDuration` 60 s per chunk request).

### File access log (who opened / downloaded which file) - `scripts/file-access-log.sql`
Decided with the user: log BOTH opening (preview) and downloading. `public.file_access_log` (no FKs: outlives deleted accounts / files; user e-mail / name, file name and project code copied in) is written ONLY by the SECURITY DEFINER RPC `log_file_access(p_file_ids uuid[], p_action text) -> uuid[]`, which records `auth.uid()` itself and only for files the caller `can_view_project`, and returns the ids now covered by the log (logged now or within the last 10 minutes = one row per person + file + action per 10 min); per-person advisory lock (no duplicate race); max 3000 new rows per person per 10 min (`LOG_RATE_LIMIT` 54000 -> 429); ~0.5 % of calls purge up to 1000 rows older than 365 days (skip locked, errors swallowed). RLS: admins read (`(select is_admin())`); no API role, not even service_role, can insert / update / delete. `POST /api/drive-url` (the only way to file BYTES) calls the RPC BEFORE signing and signs ONLY the ids it returned: single link -> `download` when `download:true`, otherwise the client's `purpose` (`view` default, `reindex` from `getFileBlob`); batch (= ZIP) -> `zip`. FAIL CLOSED: only PGRST202 (function missing = script not run) serves unlogged; any other failure -> 503 `audit_unavailable`, no link. Admin console button "ประวัติการเปิด/ดาวน์โหลดไฟล์" (`AdminAccessLog.jsx`): filters person / project / action / Thai dates (to-date = before the next Thai day), 100 rows per page by id, "CSV ทั้งหมด" exports every matching row (max 20000; BOM; = + - @ TAB CR neutralised; times with seconds). Limits (shown under the table): the action is what was REQUESTED (a view link can be saved; links work ~5 min for whoever holds them) and extracted text (`content_text`, search / AI chat) is read without a log row. Staff should be told that file access is recorded. Rollback: `scripts/file-access-log-rollback.sql` (the log is lost).

### AI chat: at most 8 files per answer
Decided with the user: the chat hands out at most `PICK_MAX` = 8 files per answer (pickable: preview / download / checkboxes / zip). A `list` answer may name up to 50 files (`LIST_MAX` in api/chat.js; the prompt asks for every match + `matchCount`, which the server clamps to [listed, files in the context]; local `searchFiles` does the same). When `max(matchCount, listed) > 8` (`isOverflow`) the chat shows `ListOverflow` instead: the tip "พบ N ไฟล์ — เกินกว่าที่ AI หยิบให้ได้ครั้งละ 8 ไฟล์ … แนะนำให้เข้าไปดาวน์โหลดที่หน้าโครงการโดยตรง", up to 6 "เปิดโครงการ X" buttons (`App.openProjectById` returns true/false; the chat closes only on success, else a toast) and the names grouped by project (click = preview), "แสดงรายชื่อ x จาก N ไฟล์" when not all are listed; no checkboxes / zip / download there. Summaries still cite <= 8 files. Non-grounded max_tokens 2500 (50 ids).

### AI chat references ("Ref n")
Grounded answers cite their sources as **[Ref n]**. `sanitizeGrounding` (api/chat.js) numbers the distinct source FILES of the passages in passage order (Ref 1 = first file read; passages of one file share a number), the DOC header shows `[P3] [Ref 2] <file>`, and the rules tell the model to label every bullet with `[Ref n]` (meeting minutes: "(รายงานการประชุม <ชุด> ครั้งที่ N) [Ref n]"; tracking data: "(ระบบเบิกงวดงาน)"). `fixRefs` canonicalises "[Ref 1, 3]" / "[ref3]" to "[Ref 1][Ref 3]" and drops numbers that do not exist. The response carries `refs: [{ref, fileId, fileName}]` (every file whose text was sent) and `trackingRef: true` when tracking briefs were sent (neither for list / download_zip, where every [Ref n] is stripped from the text). The client lists only the Refs the reply actually cites (all of them when it cites none), and strips [Ref n] from the history it sends back (numbers are per answer). `AIChat` maps refs to the local index (unknown ids are listed by name as "ไม่พบในรายการไฟล์ที่คุณเข้าถึงได้ตอนนี้"), shows an "อ้างอิง (Ref)" block (a "ระบบ" line for tracking data, then the Ref files, which also become the answer's file list for preview / zip), and renders inline "[Ref n]" as a chip that opens the file preview. The local (no AI) tracking answer (`localAnswer`, not the file-search fallback) shows the "ระบบ" reference line.

### AI features degrade gracefully when no API key is configured
The AI serverless function under `api/` (Vercel Function, plain `handler(req,res)`, not part of the Vite build) proxies to `https://api.anthropic.com/v1/messages` using `ANTHROPIC_API_KEY` from the server environment:
- `api/chat.js` — AI Document Agent chat (`POST /api/chat`): given a query + project/file context, returns intent (`list`/`download_zip`/`answer`) and matching file ids.

The other functions under `api/` (`_drive.js`, `_upload.js` (shared Google helpers for the two upload endpoints), `drive-file.js`, `drive-upload-session.js`, `drive-upload-discard.js`, `drive-url.js`) handle Google Drive storage and do not call Anthropic.

If `ANTHROPIC_API_KEY` is unset, or the Anthropic call fails/parses badly, `api/chat.js` returns `{ fallback: true }` or `{ reply: '__USE_LOCAL__' }` with HTTP 200 (never a hard error) — the client is expected to check for this signal and fall back to local logic: chat falls back to `src/utils/aiSearch.js`, a rule-based Thai/English NL search engine (synonym dictionary, time-range parsing, filters) run entirely client-side.

When adding new AI-backed features, follow this same pattern: serverless proxy + explicit fallback signal + client-side non-AI path, rather than making the AI call a hard dependency.

### Document text extraction (`src/utils/textExtract.js`)
Client-side extraction of PDF/DOCX/XLSX/TXT content (via `pdfjs-dist`, `mammoth`, `xlsx`) happens at upload time so `content_text` can be stored for search, and again on-demand via a project drawer "re-index" action for files uploaded before this feature existed. PDF.js loads its worker from a CDN (jsdelivr) rather than bundling it, deliberately, for build reliability.

**OCR (scanned PDFs and photos)** - `src/utils/ocr.js`, free and in the browser: `tesseract.js` 7 (Apache-2.0, chosen with tools-advisor; lazily imported, own chunk; its worker / wasm core / `tha+eng` language data come from jsdelivr, version-pinned by the library, cached in IndexedDB, retried with `cacheMethod: 'none'` when IndexedDB is unavailable; no document content leaves the browser). Opt-in per call: `extractTextDetailed(file, name, { ocr: true, onOcrProgress, signal })` - used by `UploadModal` and the drawer's re-index (`EXTRACTABLE_RE` includes jpg/jpeg/png/webp/bmp). Rules: a PDF is OCR'd only when its text layer averages < 20 non-space characters PER PAGE (a scan, possibly with a digital footer); when OCR succeeds the PDF's own text is kept after it (`[[TEXT]]` section), when OCR fails / finds nothing the own text (>= 5 chars) is used. Jobs run ONE AT A TIME (queue) on one shared worker; time limits: engine start 120 s, every page (getPage / render / recognize) 90 s, file 10 min; a timeout or abort replaces the worker at once (pages already read are kept) but terminates the old one only after the abandoned recognize settled or 5 s passed (tesseract.js posts the job after an async image step; terminating in between causes an uncatchable rejection); idle worker terminated after 60 s. Replies are cleaned of `[[OCR]]` / `[[OCR a/b]]` / `[[p.N]]` / `[[TEXT]]` server-side. At most 20 pages, page images ~200 dpi capped to 6 MP / 2600 px long side. `tidyOcrText`: removes a SINGLE space between two Thai letters (never next to Thai digits ๐-๙, so `๒ ๑,๕๐๐` stays two numbers; real word gaps are lost too - accepted, search falls back to words), rebuilds sara am (ํา -> ำ), drops only lines with no letter or digit at all (clause numbers, quantities, units stay). Stored format: `[[OCR]]` first line (+ ` [[OCR a/b]]` when not all pages were read), page tags `[[p.N]]` - short tags ordinary searches never hit. OCR that ran fine but found nothing stores `[[OCR]] (ไม่พบข้อความในภาพ)` (`OCR_NO_TEXT`) so re-index skips the file; `normalizeFile` turns that into `contentText: ''` + `ocrNoText: true` and `fetchFileContents` drops it, so search / chat / preview treat it as no text (chat lists it as not readable). Chat passages of OCR files carry `ocr: true` -> the DOC header says "อ่านจากภาพสแกนด้วย OCR อาจมีคำผิด" and the rules ask the model to advise checking numbers / codes against the original and never to copy the tags. OCR failure never blocks an upload (saved without text, the row says "ค้นหาได้จากชื่อไฟล์ (Re-index ภายหลังได้)"). Known limits: Tesseract sometimes drops Thai upper vowels / tone marks ("หนี้" -> "หนี"); huge photos are decoded at full size before scaling; the upload dialog has no cancel (time limits bound it). Measured locally: 4-line Thai/English image ~6 s incl. first engine download, 2-page scan ~2 s afterwards.

### File type taxonomy (`src/utils/format.js`)
Eight document types (`eia`, `drawing`, `contract`, `labor`, `standard`, `mom`, `boq`, `other`) with associated Thai labels/colors, and `detectType()` auto-classifies uploads by filename keywords (Thai + English). Version strings (`rev1`, `v2`, dates) are stripped from filenames via `deriveBaseName()`/`detectVersion()` to compute the `base_name` used for version grouping.
